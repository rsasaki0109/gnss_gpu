# PF/FGO GPU acceleration audit (2026-07-31)

## Outcome

The production-compatible PF/FGO path now has:

- a fully device-side second reduction stage for PF ESS, position spread,
  estimate, and systematic-resampling normalization;
- no host transfer or host synchronization between the stages of systematic
  resampling;
- an opt-in cuSOLVER dense Cholesky path for both basic and velocity/IMU FGO;
- an `auto` mode that keeps small systems on the CPU and selects the GPU at
  state size 512 or greater;
- automatic CPU fallback for disabled mode, insufficient GPU memory, CUDA
  allocation failure, cuSOLVER failure, or a non-positive-definite system;
- CT-RBPF/FGO and submission CLI wiring through
  `--fgo-gpu-solver off|auto|on`;
- a reproducible benchmark in `benchmarks/bench_pf_fgo_gpu.py`.

No measurement model, robust loss, state layout, acceptance gate, resampling
distribution, default PF behavior, or default FGO solver selection changed.
The submission path remains `off` by default. The CT-RBPF/FGO evaluation path
uses `auto`.

## Why these changes

The prior device PF copied `O(number_of_CUDA_blocks)` reduction partials to
the host and performed the final log-sum-exp correction on the CPU. Systematic
resampling did that twice, forcing two mid-pipeline synchronizations. The new
second-stage kernels reduce those partials on the device and transfer only one
ESS/spread scalar or four estimate scalars.

The prior FGO already assembled pseudorange normal-equation blocks on the GPU,
but every LM iteration copied the dense matrix to the CPU and used a scalar
host Cholesky implementation. The new route preserves the existing host-side
factor assembly and trial logic, then offloads only the numerically equivalent
dense factorization and solve. This makes the change independently switchable
and easy to audit.

The implementation follows NVIDIA's documented CUDA Graph/device-resident
direction and solver APIs:

- [CUDA Graphs](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html)
- [cuDSS sparse direct solver](https://docs.nvidia.com/cuda/cudss/)
- [CUB device scan](https://nvidia.github.io/cccl/unstable/cub/api/structcub_1_1DeviceScan.html)

The PF/FGO architecture is also consistent with primary RBPF work: sample the
nonlinear/multimodal state while marginalizing tractable conditional state,
and use multi-hypothesis/NLOS rejection in difficult GNSS conditions:

- [Rao-Blackwellised Particle Filtering for Dynamic Bayesian Networks](https://arxiv.org/abs/1301.3853)
- [Robust Position Estimation by RBPF without Integer Ambiguity Resolution](https://arxiv.org/abs/2506.03537)
- [GPU acceleration of the particle filter: the Metropolis resampler](https://arxiv.org/abs/1202.6163)

cuDSS is a future sparse/block-sparse backend candidate. It is not required by
this change because it is distributed separately from the CUDA Toolkit and its
API remains preview. CUDA Toolkit cuSOLVER is available on the supported build
machine and gives a safe incremental deployment path.

## Benchmark

Machine:

- NVIDIA GeForce GTX 1660 Ti, 6 GiB
- compute capability 7.5
- CUDA Toolkit 12.8
- Windows, Release build

Command:

```text
python benchmarks/bench_pf_fgo_gpu.py --particles 1000000 \
  --pf-iterations 20 --fgo-iterations 2 \
  --output results/validation/pf_fgo_gpu_benchmark_2026_07_31.json
```

PF, 1,000,000 particles:

| operation | mean | p95 | target |
|---|---:|---:|---:|
| ESS | 0.892 ms | 0.949 ms | p95 < 1.2 ms |
| estimate | 0.901 ms | 0.924 ms | p95 < 1.2 ms |
| position spread | 0.825 ms | 0.857 ms | p95 < 1.2 ms |
| systematic resample | 3.517 ms | 3.609 ms | p95 < 4.0 ms |

Direct old/new microbenchmark at 1,000,000 particles:

| operation | old mean | new mean | change |
|---|---:|---:|---:|
| ESS | 0.699 ms | 0.601 ms | 1.16x |
| estimate | 0.984 ms | 0.764 ms | 1.29x |
| position spread | 0.854 ms | 0.733 ms | 1.16x |
| systematic resample | 3.354 ms | 3.120 ms | 1.07x |

FGO, one GN iteration, 12 satellites/epoch:

| epochs | state size | CPU mean | GPU mean | speedup | max state difference |
|---:|---:|---:|---:|---:|---:|
| 50 | 200 | 4.57 ms | 7.62 ms | 0.60x | `4.55e-13` |
| 200 | 800 | 160.73 ms | 18.63 ms | 8.63x | `4.55e-13` |
| 500 | 2000 | 3283.39 ms | 87.02 ms | 37.73x | `4.55e-13` |

The state-size 512 `auto` threshold deliberately keeps the 50-epoch case on
the CPU while selecting cuSOLVER for the profitable 200/500-epoch cases.

## Real-data and fault validation

Old/new PF binaries were replayed with identical seeds on the existing PPC
Tokyo run1 and Nagoya run1 data, 100 epochs each, 10,000 particles,
`RBPF-velKF+DD`.

| run | old | new | semantic result |
|---|---:|---:|---|
| Tokyo run1 | 7.94 ms/epoch | 7.50 ms/epoch | identical PPC and 20 DD epochs |
| Nagoya run1 | 8.71 ms/epoch | 7.74 ms/epoch | identical PPC and 20 DD epochs |

The maximum ESS-ratio difference was `9.3e-13`. Timing columns were excluded
from semantic parity. These first 100 epochs have zero PPC passes in both
versions, so this run is a compatibility and runtime check, not an accuracy
claim.

Validation summary:

- 73/73 FGO tests pass with `GNSS_GPU_FGO_GPU_SOLVER=1`, including extended
  velocity/IMU state and hard-constraint paths.
- 25 FGO reference/cpu-vs-cuSOLVER parity tests pass.
- 131/131 selected PF/FGO, realtime, local-FGO, NLOS, cycle-slip, outage,
  raw-fault, and library-fault tests pass (one optional test skipped).
- CI-equivalent Python and wrapper smoke suites pass: 329 and 77 tests,
  respectively (one optional Python test skipped).
- CUDA Release targets `_gnss_gpu` and `_gnss_gpu_pf_device` build cleanly
  apart from pre-existing compiler warnings.

## Operating modes

```text
# Historical/default CPU solve
GNSS_GPU_FGO_GPU_SOLVER=0

# GPU only when state size >= 512
GNSS_GPU_FGO_GPU_SOLVER=auto

# Always attempt cuSOLVER, with automatic CPU fallback
GNSS_GPU_FGO_GPU_SOLVER=1
```

For GSDC/PF-FGO experiments, prefer the scoped CLI option:

```text
python experiments/eval_gsdc2023_ct_rbpf_fgo.py --fgo-gpu-solver auto ...
python experiments/build_gsdc2023_bridge_submission.py --fgo-gpu-solver auto ...
```
