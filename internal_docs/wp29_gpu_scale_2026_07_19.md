# WP29 GPU scale and real-time budget (2026-07-19)

## Result

WP29 passes on the locked Tokyo run2 1200-epoch production candidate arm.
The multi-position top-24 ILS proposals are evaluated by one CUDA batch per
respawn epoch. CUDA unavailability and unsupported problems fail closed; the
production path never silently falls back to CPU.

| gate | measured | threshold | status |
|---|---:|---:|---:|
| end-to-end throughput | 5.2350 epochs/s | >=5.0 | pass |
| epoch-loop throughput | 7.2653 epochs/s | >=5.0 | pass |
| epoch compute p99 | 0.6676 s | measured | pass |
| CPU/GPU FIX mismatches | 0/1200 | 0 | pass |
| CPU/GPU maximum ECEF delta | 1.42e-8 m | <=1e-7 m | pass |
| GPU audit/fast maximum ECEF delta | 0 m | <=1e-7 m | pass |
| peak RSS above start | 1.45 MB | <=4 MiB | pass |
| end RSS growth | -27.11 MB | <=4 MiB | pass |
| last-quarter RSS growth | 2.58 MB | <=4 MiB | pass |
| projected six-run time | 0.382 h | <=12 h | pass |

The average 5 Hz budget passes, but p99 is not a 5 Hz hard real-time bound:
0.668 s exceeds the 0.2 s input interval. The current claim is therefore
throughput-capable deterministic replay, not deadline-safe online execution.

The authoritative machine-readable gate is
`results/wp29/WP29_GPU_SCALE_REPORT.json`. It hashes the CPU reference,
GPU-audit, and GPU-fast summaries and trajectories.

## Implementation

- `integer_search_batch(..., engine="gpu-batch")` provides a strict batched
  adapter with the same candidate orientation and integer dtype as CPU search.
- The CUDA MLAMBDA candidate capacity is 32, covering the locked top-24 arm.
- 2,802 independent ILS problems were grouped into 201 CUDA launches.
- An 8-ambiguity/top-24 warm-up moves allocation overhead outside the epoch loop.
- `--runtime-mode fast` rejects large per-basin/integrity audit trace output.
- Summary telemetry records total/loop time, p99, CUDA work, and RSS growth.

Fast mode changes only retained diagnostics. Its 1200-row trajectory is
byte-identical to GPU audit mode, and all core counters match the CPU reference.

## Reproduction

Run the fail-closed audit after generating the CPU, GPU-audit and GPU-fast arms:

```text
python experiments/audit_wp29_gpu_scale.py \
  --cpu-summary results/wp29/csv/wp29_tdcp_imu_piecewise_route_promote_tokyo_run2_full_summary.json \
  --cpu-trajectory results/wp29/csv/wp29_tdcp_imu_piecewise_route_promote_tokyo_run2_full_trajectory.csv \
  --gpu-audit-summary results/wp29/gpu/tokyo_run2_full_summary.json \
  --gpu-audit-trajectory results/wp29/gpu/tokyo_run2_full_trajectory.csv \
  --gpu-fast-summary results/wp29/gpu/tokyo_run2_fast_summary.json \
  --gpu-fast-trajectory results/wp29/gpu/tokyo_run2_fast_trajectory.csv \
  --out-report results/wp29/WP29_GPU_SCALE_REPORT.json
```

`internal_docs/wp30_m4_production_config.json` locks this report into WP30.
The refreshed `results/wp30/WP30_M4_LOCKED_REPORT.json` validates its hash and
records the passing GPU metrics alongside the same-config Tokyo results.
